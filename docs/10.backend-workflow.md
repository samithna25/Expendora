# Backend Workflow — Expendora

## Overview

This document describes exactly what happens inside the Flask backend for every major operation in Expendora. Each workflow is broken down step by step — from the moment a request arrives at the API to the moment a response is sent back to the mobile app. This document serves as the implementation blueprint for every backend developer working on this project.

---

## Workflow Index

| # | Workflow | Trigger |
|---|---|---|
| WF-01 | User Registration | `POST /auth/register` |
| WF-02 | User Login | `POST /auth/login` |
| WF-03 | Token Refresh | `POST /auth/refresh` |
| WF-04 | Forgot Password | `POST /auth/forgot-password` |

## WF-01 User Registration

**Trigger:** `POST /api/auth/register`
**Auth:** Public

```
Mobile App sends { name, email, password }
```

### Step 1 — Receive and Parse Request

Flask receives the JSON body and extracts the three required fields: `name`, `email`, and `password`.

If any field is missing from the request body, Flask immediately returns:
```
HTTP 400 — { "success": false, "code": "MISSING_FIELDS" }
```

---

### Step 2 — Validate Input

**Email validation:**
The email is checked against a regex pattern to ensure it is correctly formatted:
```
^[\w\.-]+@[\w\.-]+\.\w{2,}$
```
If invalid → return `400 INVALID_EMAIL`

**Password validation:**
Check that `len(password) >= 8`.
If too short → return `400 WEAK_PASSWORD`

**Name validation:**
Trim whitespace, check `len(name.strip()) >= 2`.

---

### Step 3 — Check for Duplicate Email

Query MongoDB to see if any user already has this email address:
```python
db.users.find_one({ "email": email })
```
If a user is found → return `409 EMAIL_IN_USE`

---

### Step 4 — Hash the Password

Use `bcrypt` to hash the password with a salt factor of 12. The plain-text password is **never stored**:
```python
hashed = bcrypt.hashpw(password.encode('utf-8'), bcrypt.gensalt(12))
```

---

### Step 5 — Create User Document in MongoDB

Build and insert the user document:
```json
{
  "name": "Samith Narayanan",
  "email": "samith@example.com",
  "password_hash": "<bcrypt hash>",
  "currency": "MYR",
  "notifications": {
    "welcome_email": true,
    "budget_alert": true,
    "budget_exceeded": true,
    "monthly_summary": true,
    "password_reset": true
  },
  "created_at": "2026-07-08T06:00:00Z"
}
```
Capture the new MongoDB `_id` as `user_id`.

---

### Step 6 — Generate JWT Tokens

Using `Flask-JWT-Extended`:

| Token | Payload | Expiry |
|---|---|---|
| Access Token | `{ "sub": user_id }` | 15 minutes |
| Refresh Token | `{ "sub": user_id }` | 7 days |

Store a hash of the refresh token in MongoDB (used for invalidation on logout).

---

### Step 7 — Trigger Welcome Email via n8n

Flask fires an **asynchronous** HTTP POST to the n8n webhook. Flask does **not** wait for a response (fire-and-forget):
```
POST https://n8n.host/webhook/welcome-email
Body: { user_id, name, email }
```
n8n receives this and sends the welcome email independently.

---

### Step 8 — Return Success Response

```
HTTP 201 Created
{
  "success": true,
  "data": {
    "user": { id, name, email, created_at },
    "access_token": "...",
    "refresh_token": "..."
  }
}
```

## WF-02 User Login

**Trigger:** `POST /api/auth/login`
**Auth:** Public

```
Mobile App sends { email, password }
```

### Step 1 — Receive and Parse Request

Extract `email` and `password`. If either is missing → return `400 MISSING_FIELDS`.

---

### Step 2 — Look Up User by Email

```python
db.users.find_one({ "email": email })
```
If no user is found → return `401 INVALID_CREDENTIALS` (vague — do not reveal whether the email exists).

---

### Step 3 — Verify Password

```python
bcrypt.checkpw(password.encode('utf-8'), user['password_hash'])
```
If the check fails → return `401 INVALID_CREDENTIALS`

---

### Step 4 — Generate JWT Tokens

Create a new Access Token (15 min) and Refresh Token (7 days).
Store the refresh token reference in MongoDB.

---

### Step 5 — Return Success Response

```
HTTP 200 OK
{
  "success": true,
  "data": {
    "user": { id, name, email },
    "access_token": "...",
    "refresh_token": "..."
  }
}
```
The mobile app stores both tokens in `AsyncStorage` to maintain persistent sessions across app restarts.

## WF-03 Token Refresh

**Trigger:** `POST /api/auth/refresh`
**Auth:** Public (refresh token required in request body)

This workflow is triggered automatically by the mobile app whenever an API call returns `401 UNAUTHORIZED`, indicating that the access token has expired.

### Step 1 — Validate Refresh Token

Decode and verify the refresh token signature using `JWT_SECRET_KEY`.

Checks:
- Token signature is valid
- Token has not expired (within 7 days)
- Token is not in the blacklist (user has not logged out)

If any check fails → return `401 INVALID_TOKEN` (app must redirect user to Login screen).

---

### Step 2 — Issue New Access Token

Extract `user_id` from the token payload.
Generate a fresh Access Token with a 15-minute expiry.
The refresh token itself is **not rotated** at this stage.

---

### Step 3 — Return New Access Token

```
HTTP 200 OK
{
  "success": true,
  "data": { "access_token": "..." }
}
```

## WF-04 Forgot Password

**Trigger:** `POST /api/auth/forgot-password`
**Auth:** Public

```
Mobile App sends { email }
```

### Step 1 — Validate Email Field

Check the email is present and matches the valid format regex.
If invalid → return `400 INVALID_EMAIL`

---

### Step 2 — Silently Look Up User

```python
db.users.find_one({ "email": email })
```
Whether the user exists or not, the **same `200` response is always returned** to prevent email enumeration attacks.

---

### Step 3 — Generate Reset Token (only if user exists)

Generate a cryptographically secure random token:
```python
token = secrets.token_urlsafe(32)
```

Hash it before storing (never store plain-text tokens):
```python
token_hash = hashlib.sha256(token.encode()).hexdigest()
```

Insert into `db.reset_tokens`:
```json
{
  "user_id": "<ObjectId>",
  "token_hash": "<sha256 hash>",
  "expires_at": "<now + 1 hour>",
  "used": false
}
```

---

### Step 4 — Trigger Reset Email via n8n

Flask fires async HTTP POST to n8n (fire-and-forget):
```
POST /webhook/password-reset
Body: { email, reset_token: <plain token>, expires_at }
```
n8n sends the email with a deep-link URL such as:
```
expendora://reset-password?token=abc123...
```

---

### Step 5 — Return Vague Success Response

```
HTTP 200 OK
{
  "success": true,
  "message": "If this email is registered, a password reset link has been sent."
}
```
This response is returned **regardless** of whether the email was found.

## WF-05 Receipt Upload and OCR Processing

**Trigger:** `POST /api/receipts/upload`
**Auth:** Protected
**Content-Type:** `multipart/form-data`

This is the most complex workflow in Expendora. It combines file validation, cloud storage, image preprocessing, OCR text extraction, regex parsing, and category detection — all in a single request.

```
User uploads receipt image (camera or gallery)

         |
         v

STEP 1 — Authenticate Request

         |
         v

STEP 2 — Validate Image

         |
         v

STEP 3 — Upload to Cloudinary

         |
         v

STEP 4 — Preprocess Image for OCR

         |
         v

STEP 5 — Run Tesseract OCR

         |
         v

STEP 6 — Parse Raw Text with Regex

         |
         v

STEP 7 — Assign Confidence Score

         |
         v

STEP 8 — Category Detection

         |
         v

STEP 9 — Return Response (no DB save yet)
```

---

### Step 1 — Authenticate Request

`Flask-JWT-Extended` verifies the `Authorization: Bearer <token>` header.
Decode the token → extract `user_id`.
If token missing or invalid → return `401 UNAUTHORIZED`

---

### Step 2 — Validate Image

Check that the `image` field is present in the multipart form data.
If missing → return `400 NO_IMAGE`

Read the file's MIME type or extension.
Allowed types: `image/jpeg`, `image/png`
If invalid type → return `400 INVALID_FORMAT`

Check file size is <= 10 MB.

Save to a temporary path on disk:
```
/uploads/temp/<uuid>.jpg
```

---

### Step 3 — Upload to Cloudinary

Call the Cloudinary Python SDK:
```python
result = cloudinary.uploader.upload(
    temp_file_path,
    folder="expendora/receipts",
    resource_type="image"
)
receipt_url    = result['secure_url']
cloudinary_id  = result['public_id']
```

Delete the temp file from disk immediately after upload (success or failure).

If Cloudinary upload fails → return `500 UPLOAD_FAILED`

---

### Step 4 — Preprocess Image for OCR

Use `Pillow (PIL)` to improve image quality before feeding it to Tesseract. Poor-quality receipt photos are the most common cause of OCR failure — preprocessing significantly improves accuracy.

| Step | Operation | Purpose |
|---|---|---|
| 4.1 | `img.convert('L')` | Convert to grayscale — removes colour noise |
| 4.2 | `ImageEnhance.Contrast(img).enhance(2.0)` | Boost contrast — makes text stand out |
| 4.3 | `img.point(lambda x: 0 if x < 128 else 255, '1')` | Apply binary threshold — black/white only |
| 4.4 | Resize if resolution is too low | Ensure minimum effective DPI for OCR |

---

### Step 5 — Run Tesseract OCR

Pass the preprocessed image to `pytesseract`:
```python
raw_text = pytesseract.image_to_string(
    preprocessed_img,
    lang='eng+msa',        # English + Malay
    config='--psm 6'       # Uniform text block mode — best for receipts
)
```

`raw_text` is now a raw string of all text Tesseract could read from the receipt.
If pytesseract throws an exception → return `500 OCR_FAILED`

---

### Step 6 — Parse Raw Text with Regex

Apply targeted regex patterns to extract structured fields from `raw_text`:

**Extract Amount:**
Look for the largest currency value near keywords `TOTAL`, `JUMLAH`, `AMOUNT DUE`, `GRAND TOTAL`:
```python
r'(?:total|jumlah|amount due|grand total).*?(RM\s?\d+\.\d{2}|\d+\.\d{2})'
```

**Extract Date:**
Match common Malaysian receipt date formats (`DD/MM/YYYY`, `DD-MM-YYYY`, `YYYY-MM-DD`, `DD MMM YYYY`):
```python
r'\b(\d{1,2}[\/\-]\d{1,2}[\/\-]\d{2,4})\b'
```

**Extract Merchant Name:**
The merchant name typically appears in the first 1–3 lines. Take the first non-empty line and apply title-case normalisation.

**Extract Line Items:**
Scan all lines for the pattern `<description>  <amount>`:
```python
r'^(.+?)\s{2,}(\d+\.\d{2})$'
```
Collect up to 20 line items.

Any field that cannot be confidently extracted is returned as `null`. The user must fill it in manually.

---

### Step 7 — Assign Confidence Score

Count how many of the three key fields were successfully extracted: `merchant`, `amount`, `date`.

| Fields Extracted | Confidence |
|---|---|
| 3 out of 3 | `"high"` |
| 2 out of 3 | `"medium"` |
| 0 or 1 out of 3 | `"low"` |

When confidence is `"medium"` or `"low"`, the app displays a **"Please verify"** prompt so the user knows to check the pre-filled values carefully.

---

### Step 8 — Category Detection

Use the extracted `merchant` name to suggest an expense category via a keyword lookup dictionary:

```python
CATEGORY_MAP = {
  "Food": [
    "starbucks", "mcdonalds", "kfc", "subway", "tealive",
    "chatime", "mamak", "restaurant", "cafe", "warung",
    "pizzahut", "dominos", "nandos", "oldtown"
  ],
  "Transport": [
    "grab", "myrapid", "petronas", "shell", "touchngo",
    "parking", "lrt", "mrt", "ktm", "bas", "rapidkl"
  ],
  "Shopping": [
    "aeon", "uniqlo", "h&m", "zara", "shopee", "lazada",
    "guardian", "watsons", "parkson", "mydin", "ikea"
  ],
  "Bills": [
    "tnb", "indah water", "unifi", "maxis", "celcom",
    "digi", "astro", "pos malaysia", "insurance"
  ],
  "Entertainment": [
    "tgv", "gsc", "mbo", "cinema", "spotify",
    "netflix", "steam", "ticket"
  ]
}
```

Normalise merchant to lowercase, loop through `CATEGORY_MAP`. If a keyword is found → `suggested_category` = that category.
If no match → `suggested_category = null` (user selects manually).

---

### Step 9 — Return Response (No Database Save Yet)

**No data is written to MongoDB at this stage.**

The `receipt_url` and OCR-extracted data are returned to the app. The user reviews the pre-filled form, makes any corrections, then confirms — which triggers **WF-06 (Create Expense)** as a separate request.

```
HTTP 200 OK
{
  "success": true,
  "data": {
    "receipt_url": "https://res.cloudinary.com/...",
    "ocr": {
      "merchant": "Starbucks KLCC",
      "amount": 18.50,
      "date": "2026-07-07",
      "line_items": [
        { "description": "Caramel Latte", "amount": 15.00 },
        { "description": "Chocolate Muffin", "amount": 3.50 }
      ],
      "suggested_category": "Food",
      "confidence": "high"
    }
  }
}
```

### Step 1 — Authenticate Request

```python
result = db.expenses.insert_one(expense_doc)
```

```
  "message": "Expense created successfully.",
```

## WF-07 Fetch Dashboard

**Trigger:** `GET /api/dashboard?month=YYYY-MM`
**Auth:** Protected

### Step 1 — Authenticate and Parse Parameters

Verify JWT, extract `user_id`.
Read query param `month` (defaults to current month).
Parse into `start_date` (1st of month, 00:00:00) and `end_date` (last day of month, 23:59:59).

---

### Step 2 — Fetch Monthly Expenses by Category

MongoDB aggregation — groups all expenses for the month by category:
```python
db.expenses.aggregate([
  { "$match": {
      "user_id": user_id,
      "date": { "$gte": start_date, "$lte": end_date }
  }},
  { "$group": {
      "_id": "$category",
      "total": { "$sum": "$amount" },
      "count": { "$sum": 1 }
  }}
])
```
Sum all category totals → `total_spent` for the month.
Compute `percentage` for each category.

---

### Step 3 — Fetch Budget Data

```python
db.budgets.find_one({ "user_id": user_id })
```
Compute `remaining_budget = overall_budget - total_spent`.
Compute `percentage_used` per category.

---

### Step 4 — Fetch Recent Transactions

```python
db.expenses.find(
  { "user_id": user_id },
  sort=[("date", -1)],
  limit=10
)
```
Returns the 10 most recent expenses across **all time** (not filtered to the selected month).

---

### Step 5 — Generate Insight Message

Compare `total_spent` for the current month against the previous month using the same aggregation.

```python
change_pct = (current_total - prev_total) / prev_total * 100
```

| Change | Type | Example Message |
|---|---|---|
| > +20% | `"warning"` | "You spent 28% more on Food this week." |
| < -10% | `"positive"` | "Great! You saved 15% compared to last month." |
| Otherwise | `"info"` | "Your spending is on track this month." |

Also surface the top-spending category in the message if it is notable.

---

### Step 6 — Count Unread Alerts

```python
db.alerts.count_documents({ "user_id": user_id, "read": False })
```
Returns `unread_alerts` count — drives the notification badge on the dashboard screen.

---

### Step 7 — Assemble and Return Response

```
HTTP 200 OK
{
  "summary": { total_spent, total_budget, remaining_budget },
  "category_breakdown": [...],
  "recent_transactions": [...],
  "insight": { message, type },
  "unread_alerts": 2
}
```

## WF-08 Monthly Report

**Trigger:** `GET /api/reports/monthly?month=YYYY-MM`
**Auth:** Protected

### Step 1 — Authenticate and Validate

Verify JWT, validate `month` param format `YYYY-MM`. Parse `start_date` and `end_date`.

---

### Step 2 — Category Breakdown Query

MongoDB aggregation — group expenses by category for the selected month.
Compute `amount`, `percentage`, and `transactions` count per category.

---

### Step 3 — Daily Trend Query

MongoDB aggregation — group expenses by date (day):
```python
db.expenses.aggregate([
  { "$match": { "user_id": user_id, "date": { ... } } },
  { "$group": {
      "_id": { "$dateToString": { "format": "%Y-%m-%d", "date": "$date" } },
      "total": { "$sum": "$amount" }
  }},
  { "$sort": { "_id": 1 } }
])
```
Only days with at least one expense are returned.

---

### Step 4 — Month-over-Month Comparison

Determine the previous month (handle January → December of prior year).
Query total spend for previous month.
```python
difference    = current_total - previous_total
pct_change    = difference / previous_total * 100
trend         = "increased" | "decreased" | "no_change"
```

---

### Step 5 — Assemble and Return Response

```
HTTP 200 OK
{
  "month": "2026-07",
  "total_spent": 1240.50,
  "category_breakdown": [...],
  "daily_trend": [...],
  "comparison": { previous_month, previous_total, difference, percentage_change, trend }
}
```


### Step 3a — Generate CSV (if format=csv)

Use Python's built-in `csv` module to write all expense rows to an in-memory `StringIO` buffer.

Use `WeasyPrint` or `ReportLab` to render an HTML/CSS template into a PDF stored in an in-memory `BytesIO` buffer.

PDF includes:
- Report header with month and user name
- Summary table (total spent, budget, remaining)
- Category breakdown table with percentages
- Full expense list sorted by date
- Expendora branding

---

### Step 4 — Stream File Response

Set the correct response headers and stream the buffer contents:

```
Content-Type: text/csv  OR  application/pdf
Content-Disposition: attachment; filename="expendora-report-2026-07.csv"
HTTP 200 OK
```
Response body is the raw file binary — not JSON.

## WF-10 Budget Check and Email Alert

**Trigger:** Internal — called automatically after WF-06 (Create Expense)
**Auth:** N/A (internal process, not an API endpoint)

### Step 1 — Fetch Category Budget

```python
db.budgets.find_one({ "user_id": user_id })
```
Get the budget limit for the category of the newly saved expense.
If no budget is set for this category → **stop** (nothing to check).

---

### Step 2 — Calculate Total Category Spend for Current Month

```python
db.expenses.aggregate([
  { "$match": {
      "user_id": user_id,
      "category": category,
      "date": { "$gte": month_start, "$lte": month_end }
  }},
  { "$group": { "total": { "$sum": "$amount" } } }
])

pct_used = (spent / budget) * 100
```

---

### Step 3 — Evaluate Threshold and Send Alert

**If pct_used >= 80% and < 100% (Budget Warning):**

Check user notification preference `budget_alert = true`.
If enabled, fire async POST to n8n:
```
POST /webhook/budget-alert
Body: { user_id, email, category, spent, budget, percentage }
```

**If pct_used > 100% (Budget Exceeded):**

Check user notification preference `budget_exceeded = true`.
If enabled, fire async POST to n8n:
```
POST /webhook/budget-exceeded
Body: { user_id, email, category, spent, budget }
```

Both webhook calls are **fire-and-forget** — Flask does not wait for n8n.

---

### Step 4 — Log Alert in MongoDB

Insert into `db.alerts`:
```json
{
  "user_id": "<ObjectId>",
  "type": "budget_warning",
  "category": "Food",
  "spent": 420.00,
  "budget": 500.00,
  "read": false,
  "created_at": "<utcnow>"
}
```
This increments the `unread_alerts` counter shown on the dashboard notification badge.

## WF-11 Monthly Summary Email

**Trigger:** n8n cron scheduler — fires at `00:00` on the 1st of every month
**Auth:** N/A (server-to-server using `INTERNAL_API_KEY`)

### Step 1 — n8n Cron Fires

The n8n cron node is configured with the expression: `0 0 1 * *`
(midnight on the 1st of every month)

---

### Step 2 — n8n Fetches All Eligible Users

n8n HTTP node calls an internal Flask endpoint:
```
GET /api/internal/users/active
Authorization: X-Internal-Key: <INTERNAL_API_KEY>
```
Flask returns all users where `notifications.monthly_summary = true`.

---

### Step 3 — n8n Loops and Fetches Each User's Report

For each user in the list, n8n calls:
```
GET /api/reports/monthly?month=<previous_month>
Authorization: X-Internal-Key: <INTERNAL_API_KEY>
```
Flask runs WF-08 for that user and returns the full report JSON.

---

### Step 4 — n8n Composes and Sends Email

n8n's Email node (configured with SMTP or SendGrid) fills an HTML template:

| Email Section | Content |
|---|---|
| Header | User's name + "Your June 2026 Summary" |
| Total Spent | RM 1,240.50 |
| Category Table | Category, amount, percentage for each |
| Comparison | vs. previous month (↑ 26.6% or ↓ 8.2%) |
| CTA Button | "Open Expendora" deep link |

Email is sent to the user's registered address.

---

### Step 5 — n8n Logs Execution

n8n marks the workflow execution as complete.
Any delivery failures are logged in n8n's built-in execution history for review and retry.

## Error Handling Principles

| Principle | Detail |
|---|---|
| **Always return JSON** | Every response, including errors, is `application/json`. Never return raw HTML error pages. |
| **Machine-readable codes** | Every error includes a `code` field (e.g. `INVALID_EMAIL`) for the app to handle programmatically. |
| **Vague auth errors** | Login and forgot-password errors are deliberately vague to prevent user enumeration attacks. |
| **Fire-and-forget for n8n** | Flask never waits for n8n to respond. All webhook calls are async so they cannot delay API responses. |
| **No plain-text passwords** | Passwords are always bcrypt-hashed before storage. Reset tokens are sha256-hashed before storage. |
| **Temp file cleanup** | Any temp files written to disk during receipt processing are always deleted after use — on both success and failure. |
| **Background budget checks** | Budget threshold checks run in a background thread after WF-06 so they never delay the expense creation response. |
