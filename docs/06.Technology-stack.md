# Technology Stack — Expendora

## Overview

This document describes every technology used in the Expendora platform, the specific role it plays, and the rationale behind choosing it over available alternatives. Each decision was made to balance development speed, cost-efficiency, scalability, and suitability for a mobile-first personal finance application.

---

## Stack at a Glance

| Layer | Technology | Purpose |
|---|---|---|
| Mobile Frontend | React Native (Expo) | Cross-platform mobile application |
| Backend API | Flask (Python) | RESTful API server |
| Database | MongoDB Atlas | Cloud-hosted NoSQL database |
| Image Storage | Cloudinary | Receipt image upload and storage |
| OCR Engine | Tesseract OCR | Receipt text extraction |
| Workflow Automation | n8n | Email and background workflow automation |
| Authentication | JWT (JSON Web Tokens) | Stateless user authentication |
| Backend Hosting | Render / Railway | Cloud deployment of the Flask API |

## Technology Breakdown

---

### 1. React Native (Expo)

**Role:** Mobile Frontend — Cross-platform iOS & Android Application

| Attribute | Detail |
|---|---|
| **Language** | JavaScript / TypeScript |
| **Framework** | React Native via Expo SDK |
| **Targets** | iOS, Android (single shared codebase) |

#### Why React Native with Expo?

React Native allows a single JavaScript codebase to compile into native iOS and Android applications, eliminating the need to maintain two separate codebases. Expo extends this further by providing a managed workflow with pre-built native modules (camera, file system, notifications) that remove the need for native code configuration.

**Key reasons for this choice:**

- **Cross-platform efficiency** — One codebase serves both iOS and Android, halving frontend development time.
- **Expo Camera & MediaLibrary** — Built-in modules for receipt capture (camera) and gallery selection are essential to the receipt upload feature (SC-01) and are available without native setup.
- **Large ecosystem** — Access to the broader React and npm ecosystem for UI libraries, charting, and state management.
- **Expo Go** — Rapid prototyping and testing on real devices without a build step, accelerating iteration.
- **OTA Updates** — Expo allows pushing JavaScript updates directly to users without a full app store re-submission.

---

### 2. Flask (Python)

**Role:** Backend API — RESTful HTTP API Server

| Attribute | Detail |
|---|---|
| **Language** | Python 3 |
| **Framework** | Flask (micro-framework) |
| **Pattern** | RESTful API with JSON responses |

#### Why Flask?

Flask is a lightweight Python micro-framework that provides exactly what is needed for an API server without imposing unnecessary structure. Python's strength in data processing and its rich library ecosystem for OCR (Pytesseract), image handling (Pillow), and email (Flask-Mail / smtplib) make it the natural backend language for Expendora.

**Key reasons for this choice:**

- **Python + OCR synergy** — Tesseract's Python bindings (`pytesseract`) integrate directly into Flask routes, keeping the OCR pipeline within the same backend service without a separate microservice.
- **Lightweight and flexible** — Flask imposes minimal structure, allowing the API to be designed precisely as needed for Expendora's requirements.
- **Rapid development** — Python's concise syntax and Flask's simplicity mean endpoints can be built and tested quickly.
- **Rich library support** — Libraries for JWT (`Flask-JWT-Extended`), MongoDB (`PyMongo`), email, and image processing are all mature and well-documented.
- **Cost-effective hosting** — Lightweight Flask apps deploy efficiently on free and low-cost tiers of Render and Railway.

### 3. MongoDB Atlas

**Role:** Cloud Database — Primary data store for users, expenses, and reports

| Attribute | Detail |
|---|---|
| **Type** | NoSQL Document Database |
| **Hosting** | MongoDB Atlas (managed cloud, free tier available) |
| **Driver** | PyMongo |

#### Why MongoDB Atlas?

Expense records in Expendora are naturally document-shaped — each expense can contain a varying set of OCR-extracted line items, a receipt image reference, category tags, and metadata. MongoDB's flexible schema accommodates this variability without requiring rigid table migrations. Atlas provides a fully managed cloud service, removing the need to self-host and maintain a database server.

**Key reasons for this choice:**

- **Flexible schema** — Expense documents can hold optional fields (e.g., line items from OCR) without schema migration overhead, ideal for an evolving data model.
- **JSON-native** — MongoDB stores data as BSON (binary JSON), which maps directly to the JSON responses the Flask API returns to the mobile app — no ORM transformation layer required.
- **Atlas free tier** — The M0 free cluster provides sufficient storage and operations for development and early-stage usage without cost.
- **Managed hosting** — Atlas handles backups, scaling, and replication automatically, reducing operational burden.
- **Aggregation pipeline** — MongoDB's aggregation framework makes it straightforward to compute monthly spending totals, category breakdowns, and trend data required by the Reports feature (SC-04).

### 4. Cloudinary

**Role:** Image Storage — Receipt image upload, storage, and URL management

| Attribute | Detail |
|---|---|
| **Type** | Cloud Media Storage & CDN |
| **Integration** | REST API / Python SDK |
| **Free Tier** | 25 GB storage, 25 GB monthly bandwidth |

#### Why Cloudinary?

When a user uploads a receipt image, Expendora needs to store it persistently and serve it back reliably. Storing binary images directly in MongoDB is inefficient and costly. Cloudinary is a dedicated media storage service that handles upload, storage, optimisation, and CDN delivery of images — returning a stable URL that is then saved in the MongoDB expense document.

**Key reasons for this choice:**

- **Purpose-built for media** — Cloudinary is optimised for image upload and delivery, unlike general object stores.
- **Simple Python SDK** — The `cloudinary` Python package integrates directly into Flask with minimal configuration.
- **Auto-optimisation** — Cloudinary can automatically compress and resize receipt images, reducing storage costs and improving load times in the app.
- **Stable public URLs** — Each uploaded image gets a permanent CDN-backed URL, which is stored in MongoDB and displayed in the app when viewing an expense's receipt.
- **Generous free tier** — The free plan covers the expected image volumes for a personal-use application during v1.0.

### 5. Tesseract OCR

**Role:** OCR Engine — Extraction of text data from uploaded receipt images

| Attribute | Detail |
|---|---|
| **Type** | Open-source OCR engine |
| **Integration** | `pytesseract` Python wrapper |
| **Language Support** | 100+ languages including English and Malay |

#### Why Tesseract OCR?

Tesseract is the most widely used open-source OCR engine, maintained by Google. When a receipt image is uploaded to the Flask backend, Tesseract processes the image and extracts raw text. The backend then applies parsing logic to identify the merchant name, total amount, and date from the extracted text, which is returned to the app for user review (SC-02).

**Key reasons for this choice:**

- **Open-source and free** — No per-request API cost, which is critical for a personal finance app where every receipt scan must be cost-free at scale.
- **Python-native integration** — `pytesseract` wraps the Tesseract binary cleanly, making it easy to call from within Flask route handlers.
- **Runs server-side** — Processing happens entirely on the backend; no external API call latency or data privacy concerns from sending images to a third party.
- **Malay language support** — Expendora targets Malaysian users; Tesseract supports Malay (`msa`) language packs, improving accuracy on local receipts.
- **Preprocessing flexibility** — Combined with `Pillow` for image preprocessing (grayscale, contrast, thresholding), OCR accuracy on receipt images can be significantly improved.

### 6. n8n

**Role:** Workflow Automation — Email notifications and background event-driven workflows

| Attribute | Detail |
|---|---|
| **Type** | Open-source workflow automation platform |
| **Hosting** | Self-hosted (or n8n Cloud free tier) |
| **Trigger Types** | Webhook, schedule (cron), HTTP request |

#### Why n8n?

Expendora requires several automated workflows: sending welcome emails on registration, sending budget alert emails when thresholds are crossed, and delivering monthly summary emails at the end of each month (SC-05). n8n provides a visual, low-code automation platform that handles these workflows reliably without requiring bespoke background job infrastructure.

**Key reasons for this choice:**

- **Visual workflow builder** — Automated email flows can be designed, tested, and modified visually without writing and deploying additional backend code.
- **Webhook integration** — The Flask backend triggers n8n workflows via HTTP webhooks (e.g., `POST /webhook/budget-alert`), keeping automation logic decoupled from the core API.
- **Scheduled workflows** — n8n's cron scheduler handles the monthly summary email dispatch without requiring a separate task queue (Celery, etc.).
- **Email node support** — Built-in nodes for SMTP, Gmail, and SendGrid make email delivery straightforward to configure.
- **Self-hostable and free** — n8n can be self-hosted for free, keeping costs at zero for v1.0 automation needs.

### 7. JWT (JSON Web Tokens)

**Role:** Authentication — Stateless user identity and session management

| Attribute | Detail |
|---|---|
| **Standard** | RFC 7519 |
| **Library** | `Flask-JWT-Extended` (backend), `AsyncStorage` (mobile) |
| **Token Types** | Access Token (short-lived) + Refresh Token (long-lived) |

#### Why JWT?

Expendora needs a stateless authentication mechanism so that the Flask API can verify a user's identity on every request without maintaining a server-side session store. JWT tokens are self-contained: the user's identity and claims are encoded and signed within the token itself, which the mobile app stores locally and sends with each API request.

**Key reasons for this choice:**

- **Stateless** — The Flask API does not need to maintain a session database. Each request is independently authenticated by verifying the token signature — ideal for a horizontally scalable API.
- **Mobile-friendly** — The React Native app stores the JWT in `AsyncStorage` and attaches it to every API request header, which is the standard pattern for mobile API authentication.
- **Expiry control** — Short-lived access tokens (e.g., 15 minutes) paired with longer-lived refresh tokens (e.g., 7 days) balance security and user convenience, supporting persistent login sessions (FR-02.5).
- **`Flask-JWT-Extended`** — A well-maintained library that simplifies token creation, validation, refresh, and revocation within Flask.
- **Industry standard** — JWT is the de facto standard for stateless API authentication, with extensive documentation and tooling.

### 8. Render / Railway

**Role:** Backend Deployment — Cloud hosting for the Flask API server

| Attribute | Detail |
|---|---|
| **Type** | Platform-as-a-Service (PaaS) |
| **Deployment** | Git-based auto-deploy from GitHub |
| **Free Tier** | Available on both platforms for low-traffic services |

#### Why Render / Railway?

The Flask API must be accessible from the React Native mobile app over the internet. Render and Railway are modern PaaS providers that make deploying a Python Flask application as simple as connecting a GitHub repository — no server configuration, no Docker setup required. Both are evaluated as deployment targets for v1.0, with a final choice to be made based on free-tier performance during testing.

**Key reasons for this choice:**

- **Git-based auto-deploy** — Pushing to the `main` branch automatically triggers a new deployment, enabling a smooth CI/CD pipeline.
- **Zero server management** — No need to configure or maintain a VPS (Virtual Private Server); the platform handles infrastructure, TLS certificates, and uptime monitoring.
- **Free tier availability** — Both Render (free web services) and Railway (free starter tier) allow hosting the Flask API at zero cost during v1.0 development and early usage.
- **Environment variable management** — Both platforms provide secure environment variable configuration for secrets such as MongoDB connection strings, JWT secret keys, and Cloudinary credentials.
- **Simple Python support** — Both platforms natively detect and deploy Python/Flask applications from a `requirements.txt` and `Procfile` with no additional configuration.
